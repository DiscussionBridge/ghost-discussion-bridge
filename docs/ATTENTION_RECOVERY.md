# Administrator attention recovery

The r6 implementation adds `attention-recovery-1` without changing the existing V4-01–31 bodies. The native Discourse delivery panel owns **Check native state**, individual/selected **Retry**, and administrator notifications. Only actual receiver Work in `attention` gets that manual barrier. Waiting/retry_wait and local limitations keep their existing behavior.

The configured Ghost synchronization run probes the typed capability before using V4-33/34 inspection or V4-35/36 recovery routes. An unavailable/older receiver leaves this extension waiting; it does not release attention or reinterpret a normal Claim. A disabled Ghost schedule remains disabled. Run the existing `sync:publications` command deliberately, or allow an already-configured scheduler run, to consume requested checks. No new service, remote command, callback, or command-line secret is used.

Check performs current native reads under the same writer exclusion as ordinary synchronization. It checks the stable resource/native identity, exact receipt and native revision, managed fragment/title, metadata availability, pending operations and URL movement. It reads current public output through the existing anonymous verifier and rereads the native object after that observation. This path never renews a lease, applies/repairs content, updates an old receipt, replays a publication mutation or creates Work. It persists a new diagnostic/report record only. Unknown create, unknown receiver mutation, conflicting native edits or missing proof remain not-ready.

Native baseline/candidate/current content hashes use the same `ghost-owned-fragment-v1` domain. A never-applied observation uses actual empty resource and slug inventories across posts and pages; no previous publication/candidate hash is fabricated. Existing r5 exact `updated_at` revision/CAS, receipt, fragment/title and retained lifecycle/date facts remain valid baseline evidence. A new optional metadata snapshot is retained only when the ordinary receipt writer actually observes it; Check does not create retrospective metadata.

A successful check does not retry. The forum administrator's explicit action admits one linked successor Work/cycle. The durable recovery feed identifies it even when source revision and source change feed are unchanged. Ghost claims only that exact successor via V4-36, preserves the predecessor's full private context in recovery history, keeps native/resource/topic identity, and reinspects actual native state under the higher new lease before native work. It does not reset mapping fencing or reuse old acknowledgements as new success.

The initial successful new-lease check records an exact private handoff. A restart or uncertain successor acknowledgement resumes that successor's existing request/native journal under current lease/fencing, rather than comparing its own applied result to the old predecessor baseline. Lost report/claim/ack responses retain their exact mutation identity/body. A failed new cycle requires a new explicit forum action under the same approved rules.

The shared codec/schema and vendor/release identity move together to `discussionbridge-v4-core-20261025-r6`. Existing r5 To-source pending bodies and their actual artifact provenance remain retained and replayable because V4-01–31 shapes are unchanged. The separate To02 definitive invalid_field Retry and preservation422 rules are unchanged. This implementation is not a deployment or native installation qualification claim.
